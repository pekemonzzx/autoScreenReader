## 3. 改进项二：RapidOCR 默认配置有三个坑（已修复，提速 2.5–3.7×）

### 坑 1：`Det.limit_type: min` / `limit_side_len: 736` 会把小图**放大**

默认行为是「短边不足 736 就放大」。实测影响：

| 截屏区域 | 实际送入 det 的张量 | 像素量 |
| :--- | :--- | :--- |
| 900×300 | `(1,3,736,2208)` | 1.63M（原图 0.27M，**放大 6 倍**） |
| 600×160 | `(1,3,736,2752)` | 2.03M（**放大 7.9 倍**） |
| 1920×1080 | `(1,3,1088,1920)` | 2.09M（不放大，但太大） |

→ 改为 **`Det.limit_type: max` + `Det.limit_side_len: 960`**：
900×300 的 det 输入变成 `(1,3,288,896)`，det 从 310ms 降到 ~60ms。

### 坑 2：`intra_op_num_threads: auto` 在 Intel 大小核上是灾难

默认会把 ONNX Runtime 线程池铺满全部逻辑核。i7-14700KF 是 8 P-core + 12 E-core，
线程池栅栏同步要等最慢的 E-core 线程，同时自旋线程互相抢核。

同一次运行内的干净对比（900×300 合成图，5 行）：

| intra_op_num_threads | p50 | 相对 |
| :--- | :--- | :--- |
| auto（=28） | 546ms | 1.0× |
| 4 | 212ms | 2.6× |
| 8 | 171ms | 3.2× |
| **12** | **147ms** | **3.7×** |
| 16 | 225ms | 2.4× |

→ **必须显式设定，且必须在目标机上标定**（不同机器最优值不同，跨机器不能复用）。
已在 `OcrEngine` 里实现自动标定 + 缓存，并提供 `tools/tune_ocr.py`。

### 坑 3：`enable_cpu_mem_arena: false`（默认）

每次 `run()` 都重新分配全部工作内存，叠加安全软件的内存挂钩后开销明显。
→ 打开。

### 附带结论：`use_cls` 保留
竖排/翻转文本需要它。实测代价仅 ~30ms（180.6ms vs 152.2ms），保留。

## 4. OCR 延迟模型

OCR 耗时近似与**检出文本行数**成正比，与区域像素量关系较弱：

| 输入 | 行数 | p50 | ms/行 |
| :--- | :--- | :--- | :--- |
| 合成 520×140 | 3 | 62ms | 20.7 |
| 合成 900×300 | 5 | 147ms | 29.4 |
| 合成 1280×720 | 11 | 288ms | 26.2 |
| 真实浏览器 900×420 | 43 | 499ms | 11.6 |

（真实内容单行更短所以 ms/行更低，但行数多得多。）

**设计含义：**
1. **框选区域是头号延迟杠杆。** 让用户框一个紧贴的弹幕框/聊天框，而不是整屏。
2. 需要**每轮行数上限 + 早退**：行数超阈值只读前 N 行，或按 y 坐标只取关心的条带。
3. 需要**基于行数的自适应**：行数多时自动降 det 上限或只做增量读屏。

## 5. ⚠️ 重要警告：本机测量不稳定，RAM 升级已成阻塞项

同一份代码、同一张输入图、同一个 `intra=12`：

| 运行批次 | intra=12 的 p50 |
| :--- | :--- |
| 扫描 1 | **147ms** |
| 扫描 2 | 334ms |
| 扫描 3 | 382ms |

**同一配置跨批次相差 2.6 倍。** 同一次运行内的相对比较是可靠的（所以「默认 vs 调优 = 3.7×」这个结论可信），但跨批次的绝对数字不可比。

**原因（强证据）：** 本机 16GB 内存，实测**可用仅 1.3–3.5GB**（Chrome×3、KOOK、ToDesk、微信×2、钉钉等常驻吃掉 12GB+）。
ONNX Runtime 在大张量上出现超线性劣化（2.9× 像素 → 40× 耗时）和巨大抖动，典型的**内存压力/页面文件颠簸**特征。
页面文件可用 36GB，所以不会崩，只会变得又慢又不稳定。

**结论：**
- 体检报告里「加内存到 32GB 双通道」从**建议**升级为**P1 后续工作与 P2 训练的阻塞项**。
- 加内存后必须**重跑本基准**，届时出来的数字才算数。
- 目标机同样要注意：游戏 + OBS 会吃掉大量内存，本服务需要 2–3GB 余量，**目标机内存 16GB 是下限**。

### 5.1 复测：释放内存后已确证（2026-10-14 晚）

关掉 Chrome 等常驻程序，可用内存 **1.3GB → 7.5GB**，同区域（0,0,900,420）重跑：

| 指标 | 内存紧张时 | **释放后** |
| :--- | :--- | :--- |
| OCR p50 | 499ms | **396.7ms** |
| OCR p95 | 507ms | **422.6ms** |
| **批内 min→max 抖动** | — | **379.3 → 434.9ms（仅 1.15×）** |
| 跨批次抖动 | **2.6×** | **1.15×** |
| 截屏 p95 | 6.4ms | **6.0ms** |
| 识别行数 | 43 行（浏览器） | 27 行（本 GUI） |

**内存压力假设被确证**：抖动从 2.6× 降到 1.15×，绝对延迟也下降约 20%。
**测量现在可信了。**

线程扫描也随之变干净（真实屏幕 33 行）：

| intra | 4 | 6 | 8 | 10 | **12** | 16 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| p50 | 461ms | 439ms | 400ms | **365ms** | 520ms | 763ms |

- 最优值从内存紧张时的 8/12 漂到 **10**，说明**标定必须在真实负载下重跑**，缓存不能跨环境复用。
- 线程数的收益从 3.7× 缩到 **2.1×**——内存不再是瓶颈后，线程争抢的影响也变小了，
  但 16 线程（763ms）比 10 线程（365ms）慢一倍，**上限仍然必须限制**。

> **注意：这仍然不是最终数字。** 9.9GB 可用是「关掉一堆程序」换来的临时状态。
> 长期稳定的测量与 P2 训练仍建议先把内存加到 32GB 双通道。

## 6. 目标机（游戏直播机）的推算

本服务在目标机上的常驻占用：

| 资源 | 本服务占用 | 说明 |
| :--- | :--- | :--- |
| 显存 | **0**（P1 方案：OCR 走 CPU） | 全部留给游戏与 TTS |
| 内存 | ~1.5–2.5GB | ONNX 会话 + 模型 + 帧缓冲 |
| CPU | 突发 1–3 秒/次，单次 60–300ms | OCR 是突发型负载，不持续占用 |

CPU 占用点：OCR 会把 `intra_op` 个线程打满约 N 百毫秒。因为要**避免抢游戏的 CPU**，
建议在目标机上把本服务进程优先级设为 `BelowNormal`，并把 `intra_op_num_threads` 标定到
「够快但不吃满」的档位（在瓶颈拐点左侧）。

## 7. 遗留问题（P2 前处理）

1. **加内存后重跑基准**，拿到可信的绝对延迟。
2. **逐行耗时随行数增长的曲线**需要在真实直播画面上再标一次（本次用的是浏览器页面，偏密）。
3. **换更轻的模型**：本次用默认 PP-OCRv6 det_small + rec_small。可试 `det_tiny` / `rec_tiny`，
   以及 `lang_type` 限定为中文以缩小词典。
4. **DirectML 半途**：OCR 刻意走 CPU，但若目标机 CPU 弱（<6 核），需要评估 DirectML 收益
   ——  代价是与游戏抢 DX12 队列。
5. `dxcam`/`comtypes` 在解释器退出时有一次访问违例告警（不影响运行结果），
   打包时要在 `PyInstaller` 里确认不会变成崩溃。
6. mss 在远控虚拟显示器下会抓到黑屏，已在 `selfcheck()` 里做全黑检测并给出明确提示。
