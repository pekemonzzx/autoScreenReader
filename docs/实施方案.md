# 自动读屏软件实施方案 v2.1

> v1.0：初版计划（单一重装机器）
> v2.0：拆分为"本机训练打包 / 目标机免安装运行"
> **v2.1（本文件）：确认目标机 = 游戏直播机（有 N 卡）+ OBS + 自带语料训练 + 模型内置安装包 + 不考虑极低配**
> 新增核心约束：**读屏服务必须与游戏、OBS 编码共存于同一块 GPU 上**（见 §3.6）

---

## 0. 需求基线（已确认）

| # | 需求 | 对方案的影响 |
| :--- | :--- | :--- |
| 1 | 目标机有 N 卡，但配置不能高；**同时跑游戏直播 + 本服务**；**有多台且配置不一** | ⚠️ **最关键约束**：GPU 显存与算力必须精打细算。方案**必须自适应**——启动时探测显存自动分档，不做单一硬编码假设（见 §3.7） |
| 2 | 不需要授权，尽量打包，易安装 | **已定：主包（模型内置）+ GPU 运行时按需下载**（见 §4.1）；OBS 配置自动化 |
| 3 | 直播软件 = **OBS** | 音频路由可用 OBS 应用音频采集，或经 VB-CABLE；可用 obs-websocket 自动配置 |
| 4 | **用自有语料自己训练**，训练好的模型打包进安装包 | 训练流程按 GPT-SoVITS 微调走；模型体积（~700MB–1.2GB）内置 |
| 5 | 不考虑极低配机型 | 放弃云端 TTS 兜底、放弃 Windows 自带 OCR 等降级路线，专注 GPU 路径 |

## 1. 架构总览

```
━━━━━━━━━━ 本机（RTX 4080 SUPER 16G / i7-14700KF）—— 开发·训练·打包 ━━━━━━━━━━
  ① 语料处理 + 声库训练     GPT-SoVITS v2ProPlus 整合包（torch + CUDA）
  ② 模型导出                .ckpt/.pth ──► ONNX（LunaVox converter）
  ③ OCR 选型                 PP-OCR 系 ONNX 模型（det + rec + cls）
  ④ 集成调试                截屏 → OCR → 分句 → TTS → 播放
  ⑤ 打包                    产出单文件安装包（含模型）
                              │
                              ▼  拷贝安装包
━━━━━━━━━━ 目标机（游戏直播机，N 卡，Win10 2004+）━━━━━━━━━━
  ┌──────────────────────────────────────────────────────────┐
  │  GPU 资源竞争（本方案核心）                                │
  │   游戏      6–12GB 显存 + 大部分 SM                                │
  │   OBS 编码  NVENC 硬编码器（不吃 SM）+ 0.5–1.5GB 显存               │
  │   本服务 TTS  1.5–3GB 显存（v2ProPlus fp16，常驻）                 │
  │   本服务 OCR  → 走 CPU，0 显存（刻意的设计决策，见 §3.6）           │
  └──────────────────────────────────────────────────────────┘
  安装：一键安装包（程序 + OCR 模型 + 声库 ONNX + Python 运行时 + VB-CABLE 可选）
  配置：首次启动自检 + obs-websocket 自动添加音频源（可选）
```

**目标机不需要**：Python 安装、pip、conda、Docker、WSL2、Hyper-V、CUDA Toolkit、cuDNN、Visual Studio。
**目标机需要**：一张 N 卡（推荐 ≥12GB 显存）、16GB+ 内存、Windows 10 2004+、OBS。

## 2. 目标机配置要求（诚实版）

用户说"配置要求不能太高"——但因为要和游戏共用 GPU，**显存是硬门槛**，必须说清楚：

| 档 | GPU 显存 | 实际表现 | 说明 |
| :--- | :--- | :--- | :--- |
| **推荐** | **≥12GB**（RTX 4070 / 3080 12G / 4060Ti 16G / 4070Ti 及以上） | 游戏 + OBS + GPU TTS 全部共存，延迟稳定 | ✅ 主推档位 |
| 可用 | 8GB（RTX 3060Ti / 4060 / 3070） | 需限制游戏画质，或 TTS 降级到 int8 / CPU | ⚠️ 需要显存看门狗自动降级 |
| 不推荐 | ≤6GB | 游戏一开就抢不到显存 | ❌ |

| 其它 | 最低 | 推荐 |
| :--- | :--- | :--- |
| 内存 | 16GB | **32GB**（游戏 8G + OBS 2G + 服务 3G + 系统） |
| CPU | 6 核 | 8 核以上（OCR 在 CPU 上跑，需要余量） |
| 系统 | Windows 10 2004+ | Windows 11 |

> **裸机参考**：目标机空闲时，本服务常驻占用约 **2–3.5GB 显存 + 2.5–3GB 内存 + 1–2 个 CPU 核**。这个数字要在开发期实测后写进交付文档。

## 3. 逐模块方案

### 3.1 OCR：ONNX（PP-OCR 系），并且**刻意放在 CPU 上**

**为什么不用 v1 的 PaddleOCR-VL Docker：**
1. 选错模型族——PaddleOCR-**VL** 是文档解析 VLM，官方服务化是 **FastAPI + Triton + vLLM 三容器、端口 8080**，面向整页文档，单次秒级；与屏幕小块文字场景不匹配。
2. 接口对不上——v1 第 10.1 节的 `POST /api/ocr` + base64 + `options.data.format` 是 **Umi-OCR** 的接口形态，照抄跑不通。
3. Docker Desktop 要管理员 + 虚拟化 + 常驻 4–6GB 内存，且会和游戏争资源。

**v2.1 方案：**
- 引擎：**`rapidocr`**（单 wheel 27.3MB，自带 PP-OCR 系 ONNX 模型，Apache-2.0，Python ≥3.8 <4）。
- 后端：**`onnxruntime`（CPU）为默认**。
- **为什么 OCR 不放 GPU**：屏幕文字只有一块小区域，CPU 上 80–250ms 已经够用；而放到 GPU 上会和游戏抢 SM/显存，收益小、风险大。**把 GPU 全部留给游戏和 TTS。**
- 若目标机 CPU 弱（<6 核）再开 `onnxruntime-directml` 作为可选项（任意 DX12 显卡，无需 CUDA）。
- 模型档位：`mobile` det+rec 起步；屏幕字太小/太密时换 `server` 档。

### 3.2 TTS：本机训 v2ProPlus，目标机 GPU 常驻推理

**版本锁定（重要，别踩坑）：训练一律用 `v2 Pro Plus`。**
- GPT-SoVITS 官方最新已是 **V5**（带 cuda_graph / flash_attention 加速），但**只有 v2 / v2 Pro Plus 存在 ONNX 推理路径**（LunaVox）。
- 用 v2ProPlus 意味着：既能走 ONNX（体积小、依赖少），也保留走原生 torch（效果最好）的自由；先训 v5 就被锁死了。
- 官方实测 RTF：**4060Ti 0.028 / 4090 0.014**，4080S 约 0.02，即 4 秒语音约 80ms 出完。

**目标机推理形态（二选一，按显存自动切换）：**

| 形态 | 显存 | 体积 | 何时用 |
| :--- | :--- | :--- | :--- |
| **torch + CUDA（A 档，推荐）** | ~2–3GB | torch 运行时 2.5–3GB（安装包外挂） | 显存 ≥12GB 的机器 |
| **ONNX Runtime GPU（DirectML/CUDA EP）** | ~1.5–2GB | ~700MB–1.2GB（纯模型） | 显存 8–12GB，或想统一运行时 |

- 无论哪种，**模型启动后常驻显存**（不要每次重载，否则单次 3–5s）。
- 精度用 **fp16/half**，显存直接砍半。
- PyTorch 分配器加 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，减少与游戏抢显存时的碎片化 OOM。
- **中文字面前端**：LunaVox 的中文前端默认依赖 torch（`lunavox-tts[zh]`），要用纯 ONNX 路线就必须把它也导成 ONNX。**这是 P3 阶段的头号验证项**；若短期做不到，A 档直接用原生 torch 即可，纯 ONNX 路线降级为次要目标。

### 3.3 截屏：DXGI 主 / mss 回退（游戏场景下这一点变得更重要）

- 游戏可能是**独占全屏**，GDI `BitBlt` 抓不到或抓到黑屏；**DXGI Desktop Duplication**（`dxcam`）在独占全屏和无边框窗口下都能抓。
- mss 仅作回退（本机是 Console 会话，远程调试时注意远控虚拟显示器会干扰）。
- 支持手动指定**显示器索引**（多屏直播场景常见）。
- **DPI-aware**，坐标存物理像素。
- 截取策略：优先**局部区域**（用户框选聊天框/弹幕区），全屏 OCR 会显著增加 CPU 负载。

### 3.4 音频路由：OBS 已确认，两条路都可走

| 方案 | 需要装驱动 | 说明 |
| :--- | :--- | :--- |
| **A. VB-CABLE（推荐默认）** | 是（1MB 驱动，随安装包静默装） | OBS 麦克风源选 `CABLE Output`；TTS 输出到 `CABLE Input`。**主播听不到**合成音（除非在 OBS 里开监听） |
| **B. OBS 应用程序音频采集** | **否** | OBS 直接抓本服务进程的音频（Win10 2004+，需 OBS 28+）。**零驱动安装**，但主播会从系统默认设备听到合成音 |

- 播放侧：`sounddevice` + **WASAPI**，输出到 `CABLE Input`，避免重采样。
- 缓冲从 20ms 起调，爆音再加大。
- **可用 obs-websocket（OBS 28+ 内置）自动添加/配置音频源**，把"易安装"做到位：安装后启动本服务，自动在 OBS 当前场景里加一个 `CABLE Output` 音频源。这是低成本高回报的功能。
- ❌ 不要用 ToDesk Virtual Audio（远控断开即失效）。

### 3.5 文本分句与流水线（决定"游戏满载时"体感）

```
截屏 ─► OCR ─► 清洗/分句 ─► [合成队列] ─► [播放队列]
                  │             │              │
           按标点切短句    逐句 TTS      第 1 句好了就播
                          (并发上限 2)   后续边合成边播
```

- 分句：`。！？；，、` 与换行；单句超长再切。
- 合成与播放解耦（两个线程/队列）。
- **在游戏满载导致 GPU 排队时，短句策略能把一次卡顿的影响限制在一句话内**，不会让整段文字延迟。

### 3.6 【新增·核心】与游戏直播共存的资源策略

这是本方案最大的技术风险点，单独成节。

**① 显存预算表（目标机典型 12GB 卡，游戏 1080p 中高画质）**

| 占用方 | 显存 | 备注 |
| :--- | :--- | :--- |
| 游戏 | 5–8GB | 波动大，是最不可控的一项 |
| OBS 场景 + NVENC | 0.5–1.5GB | NVENC 是独立硬件单元，**不吃 SM 算力**，是好事 |
| 本服务 TTS（v2ProPlus fp16 常驻） | 1.5–3GB | 固定 |
| 本服务 OCR | 0 | 刻意放 CPU |
| **合计** | **7–12.5GB** | 12GB 卡处于临界，16GB 卡舒适 |

**② 设备选择与自动降级**
- 启动时探测可用显存（`nvidia-smi` / `torch.cuda.mem_get_info`），据此选择：GPU TTS → ONNX GPU → CPU TTS（不推荐但保命）。
- 运行中加**显存看门狗**：若分配失败或可用显存 < 阈值，自动切到低精度 / 短句 / CPU，并记日志。

**③ 计算调度（防游戏掉帧）**
- 本服务线程优先级设为 **BelowNormal**，不要抢游戏的 CPU。
- TTS 推理加**串行锁**，同时只跑 1–2 句，避免瞬时打满 GPU 导致游戏掉帧。
- OCR 在 CPU 上跑，天然不干扰 GPU。
- 提供"**直播优先模式**"开关：读屏频率限制（如最快 1 次/2 秒），游戏优先。

**④ 音频缓存（高收益）**
- 屏幕阅内容重复率很高（同一句弹幕、固定 UI 文案）。
- 加 **LRU 缓存**，键 = (文本, 音色参数, 语速)；命中直接播，延迟归零，还省 GPU。
- 建议缓存上限 200–500 条，落盘持久化。

**⑤ 满负载延迟波动（必须接受并管理）**
- 游戏占满 GPU 时，CUDA/ONNX 内核的**调度延迟不可控**，首包可能从 200ms 抖到 1s+。
- 对策：常驻模型 + 短句 + 缓存 + 串行推理；并在文档中如实说明"游戏满载时延迟会有波动"。

### 3.7 【新增】自适应分档：一份程序适配多台目标机

需求确认"有多台目标机、配置不一"，因此**不允许把显存档位写死**。启动时按下列流程自动决定运行档位，并允许用户在设置里手动覆盖。

```
启动
 ├─ 探测：nvidia-smi / torch.cuda.mem_get_info → GPU 型号 + 总显存 + 当前可用显存
 ├─ 计算"给本服务的显存预算" = 可用显存 - 游戏与 OBS 预留(默认 3GB，可调)
 └─ 分档
      预算 ≥ 3.5GB  → 档位 A：GPU TTS（torch fp16，常驻）+ OCR CPU
      预算 2–3.5GB  → 档位 B：GPU TTS（ONNX DirectML）+ OCR CPU
      预算 1–2GB    → 档位 C：GPU TTS int8 量化 + 短句上限收紧 + OCR CPU
      预算 < 1GB    → 档位 D：TTS 退 CPU（保命档，延迟明显上升，记警告日志）
```

**运行中持续校正**：显存看门狗每 N 秒复查可用显存，跌落则降档、回升不自动升档（避免抖动）。
所有档位切换都写日志，便于目标机远程排障。

**同一份安装包的适配范围**：Win10 2004+ / x64 / 任意 N 卡（8GB 起可用，12GB 起舒适）。

## 4. 打包与安装（需求 #2、#4）

### 4.1 安装包形态（已定：模型内置，GPU 运行时外挂）

| 包 | 内容 | 体积 |
| :--- | :--- | :--- |
| **主安装包（单 exe，Inno Setup / NSIS）** | 主程序 + Python 运行时 + onnxruntime + **OCR 模型 + 声库 ONNX + 参考音频**（需求 #4：模型内置）+ VB-CABLE 驱动 + OBS 配置脚本 | **约 0.6–1.5GB** |
| **GPU 加速组件包（可选，首次运行按需下载 或 随包分发）** | torch + CUDA 运行时 + cuDNN DLL（通用依赖，非模型） | 约 2.5–3GB |

**为什么这样切（已确认采用）：**
- **模型资产全部内置**在主包，满足需求 #4"训练好的模型打包进安装包"；换声库只重下主包（小），不用重下 torch（大）。
- 主包控制在 1.5GB 以内，安装/压缩都快，避免单文件 >2GB 时 Inno 压缩耗时几十分钟、部分工具链对 >2GB 支持有坑。
- torch + CUDA + cuDNN 是**通用依赖而非模型资产**，按需下载不影响"模型内置"的承诺。
- 备选（未采用）：一个包全装完，Inno Setup + LZMA2 约 3.5GB，构建与安装都慢。

### 4.2 安装器要做的自动化（"易安装"的落点）

1. 检测并静默安装 **VC++ 运行库**。
2. 可选/静默安装 **VB-CABLE** 驱动（需管理员，`VBCABLE_Setup_x64.exe -i -h` 可静默）。
3. 检测已装 OBS，若存在则通过 **obs-websocket** 自动添加音频源到当前场景。
4. 释放模型到安装目录，做一次哈希校验。
5. 建桌面快捷方式 + 可选开机自启（托盘常驻）。
6. 首次启动跑**自检**：OCR 冒烟 + TTS 冒烟 + 音频设备枚举 + 显存探测，输出诊断报告。
7. 安装路径强制 ASCII（GPT-SoVITS 生态对中文路径不稳）。

### 4.3 运行包构建

- **PyInstaller `--onedir`**（**不要 `--onefile`**：自解压慢、火绒/Defender 误报率高）。
- 本机装有**火绒**，打包输出目录务必加白名单，否则产物会被拦截或破坏。

## 5. 延迟预估（含"游戏满载"列）

| 环节 | v1 声称 | 目标机·空闲（12GB 卡） | 目标机·游戏满载 |
| :--- | :--- | :--- | :--- |
| 截屏 | 1–10ms | 5–20ms（DXGI） | 5–40ms |
| OCR | ~250ms | **80–200ms**（CPU，mobile 模型） | 100–350ms（CPU 被游戏抢） |
| TTS 首包 | 150–800ms | ~~120–300ms~~ → **实测流式 670ms（min 470ms）** | 1.0–2.0s（GPU 排队） |
| 音频路由 | 20–50ms | 20–80ms | 20–80ms |
| **端到端** | 420ms–1.1s | ~~约 250–600ms~~ → **约 750–900ms** | **约 1.0–2.4s** |

> **2026-10-14 修订**：TTS 首包实测见 [TTS训练与延迟报告.md](TTS训练与延迟报告.md)。
> 原先 120–300ms 的预估偏乐观 5–10 倍——官方 README 的 RTF 0.014–0.028 是纯模型前向的数字，
> 不含文本前端（BERT/G2PW）、参考音频特征提取与采样调度开销。
> **流式（`streaming_mode=true`）可把首包从 1786ms 压到 667ms**，是必须启用的模式。

**结论：**
- 空闲/轻载下"≤500ms"基本可达；**游戏满载时做不到稳定 500ms**，靠 §3.5 分句 + §3.6 缓存把**首句出声**压在 0.4–0.8s。
- 缓存命中时几乎无延迟。
- 这个预期必须在产品说明里写清楚，避免交付时被说"没达标"。

### 5.1 P1 实测校准（2026-10-14，详见 [P1基准报告.md](P1基准报告.md)）

| 环节 | 预估 | **实测（本机）** | 结论 |
| :--- | :--- | :--- | :--- |
| 截屏 DXGI | 5–20ms | **p50 5.4–6.0ms / p95 6.4ms** | ✅ 达标 |
| OCR（轻量区域 520×140，3 行） | 80–200ms | **62ms** | ✅ 优于目标 |
| OCR（中等区域 900×300，5 行） | 80–200ms | **147–180ms** | ✅ 达标 |
| OCR（密集区域 900×420 真实浏览器，43 行） | 80–200ms | **~500ms** | ❌ 超标 2.5× |

**三条对方案有实质影响的实测结论：**

1. **框选区域是头号延迟杠杆。** OCR 耗时近似正比于**检出文本行数**（11.6–29.4 ms/行），
   与区域像素量关系较弱。→ 必须让用户框紧贴的弹幕框/聊天框，并加**每轮行数上限 + 早退**。
2. **RapidOCR 默认配置不可用，已修好，提速 2.5–3.7×。** 三个坑：
   `Det.limit_type` 默认把短边放大到 736（900×300 被放大成 2208×736）；
   `intra_op_num_threads` 默认 auto 在 Intel 大小核上慢 3–4 倍；
   `enable_cpu_mem_arena` 默认关。细节见 `src/screenreader/ocr.py` 顶部注释。
3. **⚠️ 本机测量不稳定，RAM 升级已成阻塞项。** 同一配置跨批次相差 2.6 倍
   （intra=12：147ms / 334ms / 382ms），根因是**可用内存只剩 1.3–3.5GB**
   导致 ONNX Runtime 在大张量上超线性劣化。
   → §7 的"加内存到 32GB 双通道"从建议升级为 **P1 收尾与 P2 训练的前置条件**；
   加内存后必须重跑基准，届时数字才算数。

> 注意：目标机的 CPU 线程数需要**在本机标定后重新标定**（跨机器最优值不同），
> 已实现自动标定 + 缓存，并提供 `tools/tune_ocr.py`。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
| :--- | :--- | :--- |
| **游戏与 TTS 抢显存** | OOM / 游戏掉帧 / 服务崩 | 显存预算表 + 看门狗自动降级 + 线程低优先级 + 常驻模型 |
| **游戏满载时延迟抖动** | 直播体验不稳 | 短句流水线 + 音频 LRU 缓存 + 串行推理 + "直播优先模式" |
| 目标机实际 GPU 未知 | 无法确定档位 | 交付前用自检脚本读 `nvidia-smi` 出报告；先按 ≥12GB 设计，8GB 走降级路径 |
| **P1 实测：本机可用内存仅 1.3–3.5GB，测量跨批次抖 2.6×** | 基准不可信、训练必 OOM | **加内存到 32GB 双通道是 P1 收尾与 P2 的前置条件**（见 §5.1） |
| OCR 耗时随文本行数线性增长（~12–29 ms/行） | 框选区域过大直接超标 | 强制框选紧贴区域 + 每轮行数上限 + 早退（见 §5.1） |
| 声库版本无 ONNX 路径 | 白训 | **一律 v2 Pro Plus**，训练前定死 |
| LunaVox 中文前端依赖 torch | 纯 ONNX 路线不成立 | P3 验证；失败则 A 档走原生 torch（本需求下完全可接受） |
| 独占全屏抓屏黑屏 | 读不到字 | DXGI 优先；框选区域 + 自检时回显缩略图 |
| 火绒/Defender 拦打包产物与驱动 | 装不上 | 输出目录加白名单；安装器附信任步骤 |
| OBS 版本过旧无 obs-websocket | 自动配置失效 | 检测版本，降级为图文配置指引 |
| 中文路径 | GPT-SoVITS 组件异常 | 安装器强制 ASCII 路径 |
| 高 DPI 缩放 | 框选区域错位 | DPI-aware + 存物理像素 |

## 10. 待确认（剩余项）

已确认：目标机有 N 卡（多台、配置不一 → 走 §3.7 自适应）｜不需要授权｜OBS｜自有语料训练、模型内置｜不考虑极低配。

仍待确认：

1. **读屏内容形态**：固定框选一块区域（弹幕 / 聊天框 / 战斗信息），还是需要全屏、多区域、或跟随滚动？——决定要不要版面分析、OCR 频率上限与显存/CPU 预算。
2. **主播是否需要听到合成音**——决定 OBS 是否开监听，以及选 VB-CABLE 还是「应用程序音频采集」。
3. **游戏典型分辨率与画质**——用于把 §3.7 里"游戏与 OBS 预留"默认 3GB 调成合适的值。
4. **语料现状**：手上音频的时长、条数、是否有底噪/背景音乐——决定 P2 需要多少清洗工作（目标：干净人声 ≥1 分钟，理想 5–20 分钟）。
5. **目标机内存大小**（多台情况）——16GB 是下限，32GB 更稳。

> 以上都不阻塞 P1（截屏 + OCR 基准）的推进，可在 P2 前补齐。
